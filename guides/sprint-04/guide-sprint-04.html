1

MVVM en une page

MVVM (Model – View – ViewModel) range le code d'une application en trois rôles.

  • Le modèle (Model) — les données et les services qui les manipulent : la classe Note, le service qui lit et écrit les fichiers.
  • La vue (View) — le XAML. Elle affiche et transmet les actions de l'utilisateur, sans aucune logique.
  • Le ViewModel — la logique d'un écran, en C# ordinaire : quelles notes afficher, que faire quand on clique sur Enregistrer. Il ne connaît pas la vue, et ne contient aucun type WPF.
Depuis PHP — le ViewModel et le contrôleur Laravel
Dans Laravel, le contrôleur prépare les données ($notes = Note::latest()->get();) et les passe à la vue Blade, qui les affiche. Le ViewModel joue un rôle voisin : il prépare les données de l'écran. Deux différences : la vue va elle-même chercher les données dans le ViewModel (c'est le Binding), et elle reste reliée à lui tant que l'écran est affiché. Si une donnée change, l'écran se met à jour, sans nouvelle requête.

Le ViewModel ne connaissant pas WPF, on peut le créer et l'utiliser dans un simple test, sans fenêtre. C'est tout l'intérêt de la démarche, et l'objet du sprint 8.

Étapes dans Visual Studio

Ce que fait ce code
  • La bibliothèque n'a ni OutputType ni UseWPF : elle ne produit pas d'exécutable, et ne compile pas de XAML.
  • ProjectReference — l'application utilise la bibliothèque. La flèche ne va que dans un sens : WpfNotes.Core ne connaît pas WpfNotes.
Notion — la règle d'or : net10.0 et non net10.0-windows
La bibliothèque cible net10.0, sans -windows. Elle n'a donc pas accès aux bibliothèques propres à Windows : aucun type WPF ni MaterialDesign n'y compile. Si, par mégarde, tu écris MessageBox.Show(…) dans un ViewModel, le compilateur refuse. La séparation entre logique et interface n'est pas une bonne intention : c'est le compilateur qui la garantit.
Depuis PHP — comme un package local
C'est un peu comme découper une application Laravel en un package local (déclaré dans composer.json avec un dépôt de type path) : un morceau de code autonome, que l'application utilise, mais qui ne dépend pas d'elle.

Étape 2 — Le modèle et le service de fichiers

Interface, implémentation, injection par le constructeur.

2.1 — La classe Note

Dans WpfNotes.Core, crée un dossier Models et la classe Note. C'est la même qu'au sprint 2, dans un autre espace de noms :

WpfNotes.Core/Models/Note.cs — nouveau fichier
namespace WpfNotes.Core.Models;

public class Note
{
    // Nom du fichier sur le disque. Vaut null tant que la note n'a jamais été enregistrée.
    public string? Filename { get; set; }

    // Le texte de la note
    public string Text { get; set; } = "";

    // Date du dernier enregistrement
    public DateTime Date { get; set; }
}

2.2 — Le contrat : IFileService

Dans la version code-behind, les écrans appelaient directement File.WriteAllText. Ici, le ViewModel passera par un service : une classe dont le seul rôle est de lire et d'écrire les notes. Et il ne le connaîtra qu'à travers une interface.

Notion — à quoi sert une interface ?
Une interface est un contrat : une liste de méthodes, sans leur code. Une classe qui la « réalise » s'engage à fournir ces méthodes. Dans NoteApp, IFileService aura deux réalisations :
  • FileService, écrite juste après, qui range les notes dans des fichiers ;
  • FakeFileService, au sprint 8, qui les garde en mémoire pour les tests.
Ceux qui l'utilisent — AllNotesViewModel dans ce sprint, NoteViewModel au sprint 5 — ne connaissent que le contrat. Ils fonctionnent avec l'une comme avec l'autre, sans changer une ligne : c'est ce qui rendra les tests possibles.
Depuis PHP — les interfaces, et les contracts de Laravel
Les interfaces existent aussi en PHP (interface FileServiceInterface, puis class FileService implements FileServiceInterface). Laravel s'en sert partout sous le nom de contracts : le stockage de fichiers Illuminate\Contracts\Filesystem\Filesystem a une réalisation pour le disque local, une autre pour Amazon S3… et ton code ne voit que le contrat. En C#, le nom d'une interface commence par convention par un I : IFileService.

Crée un dossier Services dans WpfNotes.Core, puis l'interface :

WpfNotes.Core/Services/IFileService.cs — nouveau fichier
using WpfNotes.Core.Models;

namespace WpfNotes.Core.Services;

// Le contrat : ce que l'application sait faire avec les fichiers de notes.
// Ceux qui l'utilisent ne savent pas où ni comment les notes sont rangées.
public interface IFileService
{
    // Lit toutes les notes enregistrées
    List<Note> GetNotes();

    // Enregistre la note. Lui donne un nom de fichier si elle n'en a pas encore, et met sa date à jour.
    void SaveNote(Note note);

    // Supprime le fichier d'une note
    void DeleteNote(string filename);
}
Ce que fait ce code
  • public interface IFileService — un contrat de trois méthodes. Elles n'ont pas de corps : seulement leur signature, terminée par ;.
  • List<Note> GetNotes(); — renvoie une liste de notes, comme au sprint 3.
  • Pas de public devant les méthodes : dans une interface, elles le sont toutes.

2.3 — La réalisation : FileService

Le code de lecture et d'écriture de la version code-behind se range maintenant dans une seule classe :

WpfNotes.Core/Services/FileService.cs — nouveau fichier
using WpfNotes.Core.Models;

namespace WpfNotes.Core.Services;

// L'implémentation réelle du contrat : les notes sont des fichiers .txt sur le disque.
public class FileService : IFileService
{
    // Dossier où sont rangées les notes, par exemple C:\Users\toi\AppData\Local\WpfNotes\Notes
    private readonly string _folder;

    public FileService()
    {
        _folder = Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
            "WpfNotes",
            "Notes");
    }

    public List<Note> GetNotes()
    {
        Directory.CreateDirectory(_folder);

        List<Note> notes = new List<Note>();
        string[] paths = Directory.GetFiles(_folder, "*.txt");
        foreach (string path in paths)
        {
            Note note = new Note();
            note.Filename = Path.GetFileName(path);
            note.Text = File.ReadAllText(path);
            note.Date = File.GetLastWriteTime(path);
            notes.Add(note);
        }
        return notes;
    }

    public void SaveNote(Note note)
    {
        // Première sauvegarde : choisir un nom de fichier unique
        if (note.Filename == null)
        {
            note.Filename = "note-" + DateTime.Now.ToString("yyyyMMdd-HHmmss-fff") + ".txt";
        }

        Directory.CreateDirectory(_folder);
        string path = Path.Combine(_folder, note.Filename);
        File.WriteAllText(path, note.Text);
        note.Date = File.GetLastWriteTime(path);
    }

    public void DeleteNote(string filename)
    {
        string path = Path.Combine(_folder, filename);
        if (File.Exists(path))
        {
            File.Delete(path);
        }
    }
}
Ce que fait ce code
  • public class FileService : IFileService — le : sert aussi à indiquer qu'une classe réalise une interface, là où PHP écrit implements. Le compilateur vérifie que les trois méthodes du contrat sont bien présentes, avec la même signature.
  • _folder — le dossier des notes, calculé une fois dans le constructeur. Ce n'est plus un champ static de la fenêtre : c'est un détail interne du service, que personne d'autre n'a besoin de connaître.
  • GetNotes, SaveNote et DeleteNote reprennent le code des sprints 2 et 3. return notes; renvoie la liste à l'appelant.
Point de vigilance — ici, pas besoin de using System.IO;
Dans une bibliothèque de classes, System.IO fait partie des using ajoutés automatiquement, contrairement à un projet WPF. Path, File et Directory sont donc disponibles sans rien ajouter.

Étape 3 — Le premier ViewModel : la liste

ObservableCollection, propriété en lecture seule, dépendance reçue par le constructeur.

Crée un dossier ViewModels dans WpfNotes.Core, puis la classe :

WpfNotes.Core/ViewModels/AllNotesViewModel.cs — nouveau fichier
using System.Collections.ObjectModel;
using WpfNotes.Core.Models;
using WpfNotes.Core.Services;

namespace WpfNotes.Core.ViewModels;

// La logique de l'écran « liste des notes », sans aucun lien avec WPF
public class AllNotesViewModel
{
    private readonly IFileService _fileService;

    public AllNotesViewModel(IFileService fileService)
    {
        _fileService = fileService;
    }

    // Les notes affichées par la vue, la plus récente en premier
    public ObservableCollection<Note> Notes { get; } = new ObservableCollection<Note>();

    // Lit les notes et remplit la collection
    public void LoadNotes()
    {
        List<Note> notes = _fileService.GetNotes();
        List<Note> sortedNotes = notes.OrderByDescending(note => note.Date).ToList();

        Notes.Clear();
        foreach (Note note in sortedNotes)
        {
            Notes.Add(note);
        }
    }
}
Notion — recevoir ses dépendances par le constructeur
AllNotesViewModel a besoin d'un service de fichiers, mais il ne le crée pas lui-même : il le reçoit dans son constructeur. Et le type du paramètre est l'interface IFileService, pas la classe FileService : le ViewModel ne sait pas quelle réalisation il utilise. C'est celui qui crée le ViewModel qui choisit : FileService dans l'application, FakeFileService dans les tests.
Depuis PHP — l'injection dans les contrôleurs Laravel
C'est ce que tu fais dans un contrôleur Laravel quand tu écris public function __construct(private NoteRepositoryInterface $notes) : le contrôleur reçoit ce dont il a besoin, au lieu de le construire. Laravel remplit le paramètre automatiquement. Ici, pour l'instant, c'est nous qui le ferons, à la main, à l'étape 4. L'automatisme viendra au sprint 7.
Notion — ObservableCollection, une liste qui prévient
Une List<Note> ne prévient personne quand on lui ajoute ou retire un élément. Une ObservableCollection<Note>, si : elle déclenche un événement à chaque changement, et l'écran qui l'affiche se met à jour tout seul. C'est le type à utiliser pour toute collection affichée par une vue. Elle se trouve dans l'espace de noms System.Collections.ObjectModel, d'où le using en haut du fichier.
Ce que fait ce code
  • public ObservableCollection<Note> Notes { get; } = new ObservableCollection<Note>(); — une propriété en lecture seule (get sans set), initialisée avec une collection vide. La vue lira cette propriété.
  • LoadNotes() — demande les notes au service, les trie (comme au sprint 3), puis vide et remplit la collection. Chaque Notes.Add(…) fait apparaître une carte.
  • Aucun using System.Windows, aucun contrôle, aucune fenêtre : ce ViewModel est du C# ordinaire.
À tester (Ctrl+Maj+B)
La solution compile. Rien de visible pour l'instant : personne n'utilise encore le ViewModel.

Étape 4 — Relier la vue au ViewModel

DataContext, Binding vers le ViewModel, déclencheur de style.

4.1 — La vue de la liste

Dans le projet WpfNotes, crée un dossier Views et un contrôle utilisateur AllNotesView.xaml :

WpfNotes/Views/AllNotesView.xaml
<UserControl
    x:Class="WpfNotes.Views.AllNotesView"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:materialDesign="http://materialdesigninxaml.net/winfx/xaml/themes">

    <Grid>
        <ScrollViewer VerticalScrollBarVisibility="Auto">
            <!-- La collection Notes du ViewModel, une carte par note -->
            <ItemsControl Margin="8" ItemsSource="{Binding Notes}">

                <ItemsControl.ItemsPanel>
                    <ItemsPanelTemplate>
                        <WrapPanel />
                    </ItemsPanelTemplate>
                </ItemsControl.ItemsPanel>

                <ItemsControl.ItemTemplate>
                    <DataTemplate>
                        <materialDesign:Card
                            Width="220"
                            Height="160"
                            Margin="8"
                            Padding="16">
                            <DockPanel>
                                <TextBlock
                                    DockPanel.Dock="Bottom"
                                    FontSize="12"
                                    Opacity="0.7"
                                    Text="{Binding Date, StringFormat='dd/MM/yyyy HH:mm'}" />
                                <TextBlock
                                    Text="{Binding Text}"
                                    TextTrimming="CharacterEllipsis"
                                    TextWrapping="Wrap" />
                            </DockPanel>
                        </materialDesign:Card>
                    </DataTemplate>
                </ItemsControl.ItemTemplate>

            </ItemsControl>
        </ScrollViewer>

        <!-- Visible seulement quand la collection est vide -->
        <TextBlock
            HorizontalAlignment="Center"
            VerticalAlignment="Center"
            Opacity="0.7"
            Text="Aucune note.">
            <TextBlock.Style>
                <Style TargetType="TextBlock">
                    <Setter Property="Visibility" Value="Collapsed" />
                    <Style.Triggers>
                        <DataTrigger Binding="{Binding Notes.Count}" Value="0">
                            <Setter Property="Visibility" Value="Visible" />
                        </DataTrigger>
                    </Style.Triggers>
                </Style>
            </TextBlock.Style>
        </TextBlock>
    </Grid>
</UserControl>
WpfNotes/Views/AllNotesView.xaml.cs
using System.Windows.Controls;

namespace WpfNotes.Views;

public partial class AllNotesView : UserControl
{
    public AllNotesView()
    {
        InitializeComponent();
    }
}
Ce que fait ce code
  • ItemsSource="{Binding Notes}" — au sprint 3, le code-behind écrivait NotesList.ItemsSource = sortedNotes;. Ici, la vue va elle-même chercher la propriété Notes de son ViewModel. L'ItemsControl n'a plus besoin de nom.
  • Le DataTemplate d'une carte est le même qu'au sprint 3, sans le bouton : ouvrir une note arrive au sprint 5.
  • Le code-behind ne contient que InitializeComponent() : la vue n'a plus aucune logique.
Notion — le déclencheur de style (DataTrigger)
Au sprint 3, le code-behind masquait le message « Aucune note » avec un if. La vue n'a plus de code : c'est le XAML qui s'en charge. Le Style du texte fixe sa visibilité à Collapsed ; le DataTrigger la passe à Visible quand Notes.Count vaut 0. Comme la collection prévient de ses changements, le message apparaît et disparaît tout seul.

4.2 — La fenêtre, et l'assemblage à la main

Remplace le contenu de MainWindow.xaml par :

WpfNotes/MainWindow.xaml
<Window
    x:Class="WpfNotes.MainWindow"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:materialDesign="http://materialdesigninxaml.net/winfx/xaml/themes"
    xmlns:views="clr-namespace:WpfNotes.Views"
    Title="WpfNotes"
    Width="900"
    Height="600"
    WindowStartupLocation="CenterScreen"
    Background="{DynamicResource MaterialDesignPaper}"
    FontFamily="{materialDesign:MaterialDesignFont}"
    TextElement.Foreground="{DynamicResource MaterialDesignBody}">

    <DockPanel>

        <!-- Barre d'application : le titre -->
        <materialDesign:ColorZone
            Padding="16"
            DockPanel.Dock="Top"
            Mode="PrimaryMid">
            <TextBlock FontSize="20" Text="Mes notes" />
        </materialDesign:ColorZone>

        <!-- La liste des notes ; elle hérite du DataContext de la fenêtre -->
        <views:AllNotesView />

    </DockPanel>
</Window>
Ce que fait ce code
xmlns:views="clr-namespace:WpfNotes.Views" déclare un préfixe pour les classes de l'espace de noms WpfNotes.Views ; <views:AllNotesView /> place alors la vue dans la fenêtre, sous la barre de titre.

Puis le code-behind de la fenêtre :

WpfNotes/MainWindow.xaml.cs
using System.Windows;
using WpfNotes.Core.Services;
using WpfNotes.Core.ViewModels;

namespace WpfNotes;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();

        // On assemble les pièces à la main : le service, puis le ViewModel qui l'utilise
        IFileService fileService = new FileService();
        AllNotesViewModel viewModel = new AllNotesViewModel(fileService);
        viewModel.LoadNotes();

        // Le ViewModel devient la source des Binding de la fenêtre et de ce qu'elle contient
        DataContext = viewModel;
    }
}
Notion — le DataContext, la source des Binding
Au sprint 3, chaque carte avait sa note pour DataContext. Le principe est le même pour la fenêtre : DataContext = viewModel; fait du ViewModel la source de tous ses Binding. Et le DataContext se transmet aux enfants : AllNotesView, placée dans la fenêtre, hérite du même ViewModel. C'est pour cela que {Binding Notes} trouve la collection.
Ce que fait ce code
  • IFileService fileService = new FileService(); — la variable a le type de l'interface, et contient un objet de la classe qui la réalise. C'est la seule ligne de l'application qui nomme FileService.
  • new AllNotesViewModel(fileService) — on fournit au ViewModel le service qu'il attend.
  • viewModel.LoadNotes(); — on charge les notes avant d'afficher la fenêtre.
Point de vigilance — un Binding qui ne trouve rien ne dit rien
Si tu écris {Binding Note} au lieu de {Binding Notes}, aucune erreur de compilation : la liste reste simplement vide. WPF signale le problème dans la fenêtre Sortie de Visual Studio, pendant l'exécution, avec une ligne qui commence par System.Windows.Data Error. C'est le premier endroit à regarder quand un écran n'affiche pas ce qu'il devrait.
À tester (F5)
  1. La liste affiche les notes créées avec la version code-behind : les deux versions partagent le même dossier, %LocalAppData%\WpfNotes\Notes.
  2. Si le dossier est vide, le message « Aucune note. » s'affiche. Ajoute à la main un fichier test.txt dans le dossier, relance : une carte apparaît.
