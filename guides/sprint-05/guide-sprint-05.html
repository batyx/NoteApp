Étape 1 — Deux contrats et le ViewModel d'une note

MVVM Toolkit, ObservableObject, propriété et commande générées.

1.1 — Installer le MVVM Toolkit

Installe le package NuGet CommunityToolkit.Mvvm, version 8.4.0, dans le projet WpfNotes.Core. Le .csproj de la bibliothèque devient :

Notion — un package qui écrit du code pour toi
Le MVVM Toolkit de Microsoft fournit des classes de base pour les ViewModels, et surtout des générateurs de code : tu places un attribut ([ObservableProperty], [RelayCommand]) devant un champ ou une méthode, et le compilateur écrit pour toi le code répétitif qui va avec. Ce code n'apparaît pas dans tes fichiers, mais il est bien compilé. Chaque fois qu'on utilise un attribut, un encadré montre ce qu'il génère.
Point de vigilance — le Toolkit va dans WpfNotes.Core
Le Toolkit ne dépend pas de WPF : il respecte la règle d'or, et c'est dans la bibliothèque que vivent les ViewModels. Ne l'installe pas dans le projet WpfNotes : il en profite déjà grâce à la référence de projet.

1.2 — Deux nouveaux contrats

Dans la version code-behind, l'écran d'une note appelait directement la fenêtre pour changer d'écran (mainWindow.ShowAllNotes()) et afficher un message (mainWindow.ShowMessage(…)). Un ViewModel ne connaît pas la fenêtre : il passera par deux contrats.

Notion — à quoi servent ces deux interfaces ?
  • INavigationService — changer d'écran. Elle sera utilisée par AllNotesViewModel (bouton « + », clic sur une carte) et par NoteViewModel (Enregistrer, Annuler). Deux réalisations : MainViewModel, à l'étape 2, qui change vraiment d'écran, et FakeNavigationService, au sprint 8, qui retient seulement l'écran demandé.
  • INotificationService — afficher un message. Elle sera utilisée par NoteViewModel. Deux réalisations : NotificationService, dans le projet WPF, qui utilise le Snackbar, et FakeNotificationService, au sprint 8, qui garde les messages dans une liste.
Dans les deux cas, le ViewModel ne sait pas laquelle il utilise : il respecte le contrat, c'est tout.
WpfNotes.Core/Services/INavigationService.cs — nouveau fichier
using WpfNotes.Core.Models;

namespace WpfNotes.Core.Services;

// Changer d'écran. Les ViewModels demandent un écran ; ils ne savent pas comment il s'affiche.
public interface INavigationService
{
    // Affiche la liste des notes
    void NavigateToAllNotes();

    // Affiche l'écran d'une note : une note existante, ou une note neuve
    void NavigateToNote(Note note);
}
WpfNotes.Core/Services/INotificationService.cs — nouveau fichier
namespace WpfNotes.Core.Services;

// Afficher un court message à l'utilisateur.
// L'implémentation réelle utilise le Snackbar de MaterialDesign, dans le projet WPF.
public interface INotificationService
{
    void Show(string message);
}

1.3 — Le ViewModel d'une note

Crée NoteViewModel dans le dossier ViewModels :

WpfNotes.Core/ViewModels/NoteViewModel.cs — nouveau fichier
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;
using WpfNotes.Core.Models;
using WpfNotes.Core.Services;

namespace WpfNotes.Core.ViewModels;

// La logique de l'écran « une note »
public partial class NoteViewModel : ObservableObject
{
    private readonly Note _note;
    private readonly IFileService _fileService;
    private readonly INotificationService _notificationService;
    private readonly INavigationService _navigationService;

    public NoteViewModel(
        Note note,
        IFileService fileService,
        INotificationService notificationService,
        INavigationService navigationService)
    {
        _note = note;
        _fileService = fileService;
        _notificationService = notificationService;
        _navigationService = navigationService;

        Text = note.Text;
    }

    // Le texte en cours d'édition, lié au champ de saisie de la vue
    [ObservableProperty]
    private string _text = "";

    // La ligne affichée en haut de l'écran
    public string DateText
    {
        get
        {
            if (_note.Filename == null)
            {
                return "Nouvelle note";
            }
            return "Enregistrée le " + _note.Date.ToString("dd/MM/yyyy HH:mm");
        }
    }

    // Bouton Annuler : revenir à la liste sans rien enregistrer
    [RelayCommand]
    private void Cancel()
    {
        _navigationService.NavigateToAllNotes();
    }

    // Bouton Enregistrer : écrire la note, prévenir l'utilisateur, revenir à la liste
    [RelayCommand]
    private void Save()
    {
        _note.Text = Text;
        _fileService.SaveNote(_note);

        _notificationService.Show("Note enregistrée");
        _navigationService.NavigateToAllNotes();
    }
}
Notion — ObservableObject, un ViewModel qui prévient la vue
Une vue reliée à une propriété doit être prévenue quand cette propriété change, sinon elle continue d'afficher l'ancienne valeur. En .NET, ce mécanisme porte un nom : l'interface INotifyPropertyChanged et son événement PropertyChanged. La classe de base ObservableObject, fournie par le Toolkit, réalise cette interface : NoteViewModel : ObservableObject en hérite.
Code généré par le Toolkit — [ObservableProperty]

Devant le champ privé _text, l'attribut [ObservableProperty] génère une propriété publique Text (le nom du champ, sans le _, avec une majuscule). En simplifiant, le code généré est :

Code généré (simplifié) — la propriété Text
public string Text
{
    get
    {
        return _text;
    }
    set
    {
        if (_text != value)
        {
            _text = value;
            OnPropertyChanged("Text");   // prévient la vue
        }
    }
}

À chaque modification, OnPropertyChanged (hérité d'ObservableObject) déclenche l'événement PropertyChanged : la vue relit la valeur. C'est pour pouvoir ajouter ce code à ta classe que le générateur exige le mot partial, comme pour le XAML.

Code généré par le Toolkit — [RelayCommand]

Devant la méthode Save(), l'attribut [RelayCommand] génère une propriété SaveCommand : une commande qui appelle Save(). En simplifiant :

Code généré (simplifié) — la commande SaveCommand
private RelayCommand? _saveCommand;

public IRelayCommand SaveCommand
{
    get
    {
        if (_saveCommand == null)
        {
            // la commande appellera Save()
            _saveCommand = new RelayCommand(Save);
        }
        return _saveCommand;
    }
}

De même, Cancel() donne CancelCommand.

Notion — la commande remplace le gestionnaire de clic
Dans la version code-behind, un bouton appelait une méthode du code-behind (Click="SaveButton_Click"). En MVVM, un bouton se relie à une commande du ViewModel : Command="{Binding SaveCommand}". Une commande est un objet qui sait s'exécuter (Execute) et dire s'il peut l'être (CanExecute, au sprint 6). Le ViewModel n'a pas besoin de savoir qu'un bouton existe : un test pourra appeler SaveCommand.Execute(null) directement.
Depuis PHP — une commande, c'est un peu une route
Dans Laravel, un formulaire Blade ne contient pas le code d'enregistrement : il désigne une action (action="{{ route('notes.store') }}"), et c'est le contrôleur qui fait le travail. Ici, le bouton désigne une commande ({Binding SaveCommand}), et c'est le ViewModel qui fait le travail.
Ce que fait ce code
  • Le constructeur reçoit la note à éditer, puis les trois services. Il recopie le texte de la note dans la propriété Text, que la vue affichera.
  • DateText — une propriété calculée, en lecture seule (get seulement) : elle reprend le if de UpdateDisplay du sprint 2. Elle n'a pas besoin de prévenir la vue : sa valeur ne change pas tant que l'écran est affiché.
  • Save() — recopie le texte dans la note, la fait enregistrer par le service, puis demande un message et le retour à la liste, chacun par son contrat.
  • Cancel() — revient à la liste sans toucher à la note : le texte modifié n'est recopié dans la note que par Save().

La solution compile. L'application fonctionne comme au sprint 4 : personne n'utilise encore les nouvelles classes.

Étape 2 — Naviguer en changeant de ViewModel

ViewModel principal, DataTemplate par type, commande avec paramètre, assemblage dans App.

2.1 — Le principe

Dans la version code-behind, la fenêtre changeait d'écran en plaçant une vue dans sa zone MainContent. En MVVM, c'est un ViewModel qui décide : MainViewModel, le ViewModel de la fenêtre, expose une propriété CurrentViewModel. La fenêtre l'affiche, et WPF choisit la vue qui correspond à son type.

2.2 — Les commandes de la liste

Remplace le contenu de AllNotesViewModel.cs :

WpfNotes.Core/ViewModels/AllNotesViewModel.cs
using System.Collections.ObjectModel;
using CommunityToolkit.Mvvm.Input;
using WpfNotes.Core.Models;
using WpfNotes.Core.Services;

namespace WpfNotes.Core.ViewModels;

// La logique de l'écran « liste des notes », sans aucun lien avec WPF
public partial class AllNotesViewModel
{
    private readonly IFileService _fileService;
    private readonly INavigationService _navigationService;

    public AllNotesViewModel(IFileService fileService, INavigationService navigationService)
    {
        _fileService = fileService;
        _navigationService = navigationService;
    }

    // Les notes affichées par la vue, la plus récente en premier
    public ObservableCollection<Note> Notes { get; } = new ObservableCollection<Note>();

    // Lit les notes et remplit la collection
    public void LoadNotes()
    {
        List<Note> notes = _fileService.GetNotes();
        List<Note> sortedNotes = notes.OrderByDescending(note => note.Date).ToList();

        Notes.Clear();
        foreach (Note note in sortedNotes)
        {
            Notes.Add(note);
        }
    }

    // Bouton « + » : ouvrir une note neuve
    [RelayCommand]
    private void NewNote()
    {
        Note newNote = new Note();
        _navigationService.NavigateToNote(newNote);
    }

    // Clic sur une carte : ouvrir la note qu'elle affiche
    [RelayCommand]
    private void OpenNote(Note note)
    {
        _navigationService.NavigateToNote(note);
    }
}
Ce que fait ce code
  • Le constructeur reçoit en plus un INavigationService.
  • partial — nécessaire pour que le Toolkit ajoute les commandes à la classe.
  • NewNote() → NewNoteCommand : crée une note neuve et demande à l'ouvrir.
  • OpenNote(Note note) → OpenNoteCommand : une commande avec paramètre. La vue lui transmettra la note de la carte cliquée.

2.3 — Le ViewModel de la fenêtre

Crée MainViewModel dans le dossier ViewModels :

WpfNotes.Core/ViewModels/MainViewModel.cs — nouveau fichier
using CommunityToolkit.Mvvm.ComponentModel;
using WpfNotes.Core.Models;
using WpfNotes.Core.Services;

namespace WpfNotes.Core.ViewModels;

// Le ViewModel de la fenêtre. Il expose l'écran courant, et c'est lui qui change d'écran :
// il joue donc aussi le rôle du service de navigation.
public partial class MainViewModel : ObservableObject, INavigationService
{
    private readonly IFileService _fileService;
    private readonly INotificationService _notificationService;
    private readonly AllNotesViewModel _allNotesViewModel;

    public MainViewModel(IFileService fileService, INotificationService notificationService)
    {
        _fileService = fileService;
        _notificationService = notificationService;

        // La liste existe pendant toute la vie de l'application ; « this » est son service de navigation
        _allNotesViewModel = new AllNotesViewModel(fileService, this);
        _allNotesViewModel.LoadNotes();

        // Au démarrage, on affiche la liste
        NavigateToAllNotes();
    }

    // Le ViewModel de l'écran affiché ; la fenêtre choisit la vue qui lui correspond
    [ObservableProperty]
    private object? _currentViewModel;

    public void NavigateToAllNotes()
    {
        CurrentViewModel = _allNotesViewModel;
    }

    public void NavigateToNote(Note note)
    {
        NoteViewModel noteViewModel = new NoteViewModel(note, _fileService, _notificationService, this);
        CurrentViewModel = noteViewModel;
    }
}
Depuis PHP — hériter d'une classe et réaliser une interface
class MainViewModel : ObservableObject, INavigationService s'écrirait en PHP class MainViewModel extends ObservableObject implements NavigationServiceInterface. En C#, le : sert pour les deux : d'abord la classe parente (une seule), puis les interfaces, séparées par des virgules.
Ce que fait ce code
  • [ObservableProperty] private object? _currentViewModel; — génère la propriété CurrentViewModel, qui prévient la fenêtre à chaque changement d'écran. Son type est object? : elle contient tantôt un AllNotesViewModel, tantôt un NoteViewModel.
  • new AllNotesViewModel(fileService, this) — MainViewModel réalise INavigationService : il se passe lui-même (this) comme service de navigation. La liste est créée une seule fois et chargée au démarrage.
  • NavigateToNote — crée un NoteViewModel neuf pour chaque note ouverte, et lui fournit tout ce dont il a besoin.
Point de vigilance — un compromis assumé
MainViewModel fait deux métiers : ViewModel de la fenêtre, et service de navigation. Dans un projet plus grand, on écrirait une classe NavigationService à part. Ici, ce choix garde le code court, sans changer l'essentiel : les autres ViewModels ne connaissent que le contrat INavigationService.

2.4 — Associer chaque ViewModel à sa vue

Remplace le contenu de App.xaml :

WpfNotes/App.xaml
<Application
    x:Class="WpfNotes.App"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:materialDesign="http://materialdesigninxaml.net/winfx/xaml/themes"

    xmlns:views="clr-namespace:WpfNotes.Views">
    <!-- Pas de StartupUri : c'est App.xaml.cs qui crée la fenêtre -->
    <Application.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <materialDesign:BundledTheme
                    BaseTheme="Light"
                    PrimaryColor="DeepPurple"
                    SecondaryColor="Lime" />
                <ResourceDictionary Source="pack://application:,,,/MaterialDesignThemes.Wpf;component/Themes/MaterialDesign3.Defaults.xaml" />
            </ResourceDictionary.MergedDictionaries>

            <!-- Pour chaque type de ViewModel, la vue qui l'affiche -->
            <DataTemplate DataType="{x:Type viewModels:AllNotesViewModel}">
                <views:AllNotesView />
            </DataTemplate>
            <DataTemplate DataType="{x:Type viewModels:NoteViewModel}">
                <views:NoteView />
            </DataTemplate>
        </ResourceDictionary>
    </Application.Resources>
</Application>
Notion — le DataTemplate associé à un type
Au sprint 3, un DataTemplate décrivait l'apparence d'une note dans la liste. Placé dans les ressources de l'application avec DataType="{x:Type …}", il devient une règle générale : « chaque fois qu'un objet de ce type doit être affiché, utilise cette vue ». Quand CurrentViewModel contient un NoteViewModel, WPF crée donc une NoteView et lui donne ce ViewModel pour DataContext.
Ce que fait ce code
  • xmlns:viewModels="clr-namespace:WpfNotes.Core.ViewModels;assembly=WpfNotes.Core" — un préfixe pour les classes d'un autre projet : assembly= nomme la bibliothèque.
  • StartupUri a disparu : la fenêtre a maintenant besoin d'un ViewModel pour exister. C'est App.xaml.cs qui la créera, en 2.6.

2.5 — La notification et la fenêtre

La réalisation de INotificationService utilise le Snackbar : elle vit donc dans le projet WPF. Crée un dossier Services dans WpfNotes :

WpfNotes/Services/NotificationService.cs — nouveau fichier
using MaterialDesignThemes.Wpf;
using WpfNotes.Core.Services;

namespace WpfNotes.Services;

// L'implémentation réelle de INotificationService : le Snackbar de MaterialDesign.
// Elle vit dans le projet WPF, la seule partie de l'application qui connaît MaterialDesign.
public class NotificationService : INotificationService
{
    private readonly SnackbarMessageQueue _messageQueue;

    public NotificationService(SnackbarMessageQueue messageQueue)
    {
        _messageQueue = messageQueue;
    }

    public void Show(string message)
    {
        _messageQueue.Enqueue(message);
    }
}
Ce que fait ce code
La classe reçoit la file de messages du Snackbar (SnackbarMessageQueue) et y ajoute chaque message. C'est, avec la fenêtre, la seule classe de l'application qui sache qu'un Snackbar existe.

Remplace le contenu de MainWindow.xaml et de MainWindow.xaml.cs :

2.6 — Assembler l'application dans App

Remplace le contenu de App.xaml.cs :

WpfNotes/App.xaml.cs
using System.Windows;
using MaterialDesignThemes.Wpf;
using WpfNotes.Core.Services;
using WpfNotes.Core.ViewModels;
using WpfNotes.Services;

namespace WpfNotes;

public partial class App : Application
{
    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);

        // On assemble l'application à la main : chaque objet reçoit ce dont il a besoin
        IFileService fileService = new FileService();
        SnackbarMessageQueue messageQueue = new SnackbarMessageQueue(TimeSpan.FromSeconds(2));
        INotificationService notificationService = new NotificationService(messageQueue);
        MainViewModel mainViewModel = new MainViewModel(fileService, notificationService);

        MainWindow mainWindow = new MainWindow(mainViewModel, messageQueue);
        mainWindow.Show();
    }
}
Ce que fait ce code
  • protected override void OnStartup(…) — redéfinit une méthode de la classe parente Application, appelée au lancement. override signale qu'on remplace une méthode héritée ; PHP le fait sans mot-clé. base.OnStartup(e); appelle d'abord la version d'origine, comme parent:: en PHP.
  • Les objets sont créés dans l'ordre : chacun reçoit ceux dont il a besoin, qui doivent donc exister avant lui. C'est l'assemblage de l'application, le seul endroit qui nomme les classes concrètes.
  • TimeSpan.FromSeconds(2) — chaque message reste affiché deux secondes.

2.7 — Les vues

Remplace le contenu de AllNotesView.xaml : les cartes redeviennent des boutons, et le bouton « + » revient.

Notion — atteindre la commande depuis une carte
Dans le DataTemplate d'une carte, le DataContext est la note de la carte. Or la commande OpenNoteCommand appartient au ViewModel de la liste. Le Binding remonte donc l'arbre : RelativeSource={RelativeSource AncestorType=ItemsControl} désigne l'ItemsControl qui contient la carte, et DataContext.OpenNoteCommand prend la commande dans son DataContext, le ViewModel de la liste. CommandParameter="{Binding}" transmet à la commande la note de la carte elle-même.

Ce que fait ce code
  • Text="{Binding Text, UpdateSourceTrigger=PropertyChanged}" — un Binding dans les deux sens : le champ affiche Text, et chaque frappe met à jour Text dans le ViewModel. UpdateSourceTrigger=PropertyChanged fait la mise à jour à chaque caractère, au lieu d'attendre que le champ perde le focus.
  • Les boutons n'ont plus de Click : Command="{Binding SaveCommand}" et Command="{Binding CancelCommand}".
  • Plus aucun x:Name : le code-behind n'a plus rien à manipuler.

Étape 3 — Un problème à résoudre

Pourquoi une note neuve n'apparaît pas dans la liste.

À tester (F5)
Crée une note neuve et enregistre-la. Le message « Note enregistrée » s'affiche… mais la carte n'apparaît pas dans la liste. Ferme l'application et relance-la : la note est bien là.

Le fichier a été écrit : c'est la liste qui n'est pas à jour. Trois faits l'expliquent.

  1. MainViewModel crée AllNotesViewModel une seule fois, et ne le charge qu'au démarrage.
  2. NoteViewModel enregistre la note, mais ne connaît pas la liste : il ne peut pas lui ajouter la nouvelle note.
  3. Pour une note existante, tout semble marcher : la carte et l'écran partagent le même objet Note (une référence, comme au sprint 2), et la vue de la liste est recréée à chaque retour. Mais la carte ne remonte pas en tête de liste.

Plusieurs solutions sont possibles :

  • Recharger toute la liste à chaque retour, comme la version code-behind : simple, mais on relit le disque à chaque fois.
  • Donner à NoteViewModel une référence vers AllNotesViewModel : les deux ViewModels deviendraient liés l'un à l'autre, et chacun serait plus difficile à tester seul.
  • Faire envoyer un message par NoteViewModel : « cette note vient d'être enregistrée ». Qui veut l'entendre l'écoute ; l'émetteur ne sait pas qui le reçoit. C'est la solution du sprint 6.
