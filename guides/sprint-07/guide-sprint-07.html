L'injection de dépendances

Chaque classe reçoit maintenant ce dont elle a besoin par son constructeur. Mais quelqu'un doit encore tout créer, dans le bon ordre : c'est App.xaml.cs, à la main. Dans ce sprint court, tu confies ce travail à un conteneur d'injection de dépendances, l'équivalent du conteneur de services de Laravel.

Où en est-on ? Que va-t-on faire ?

À la fin du sprint 6, l'application est complète : liste, édition, enregistrement, suppression avec confirmation, messages entre ViewModels. Aucun ViewModel ne crée ses services : il les reçoit. C'est App.xaml.cs qui crée tous les objets, à la main, dans le bon ordre.

Pour ce sprint : trois étapes.

  • Étape 1 — comprendre ce que fait l'assemblage à la main, et ses limites.
  • Étape 2 — le remplacer par un conteneur.
  • Étape 3 — vérifier que rien d'autre n'a changé, et lire une erreur du conteneur.
1

Étape 1 — Ce que fait l'assemblage à la main

Un graphe de dépendances.

Relis App.xaml.cs tel qu'il est à la fin du sprint 6 :

WpfNotes/App.xaml.cs — fin du sprint 6
using System.Windows;
using CommunityToolkit.Mvvm.Messaging;
using MaterialDesignThemes.Wpf;
using WpfNotes.Core.Services;
using WpfNotes.Core.ViewModels;
using WpfNotes.Services;

namespace WpfNotes;

public partial class App : Application
{
    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);

        // On assemble l'application à la main : chaque objet reçoit ce dont il a besoin
        IFileService fileService = new FileService();
        IDialogService dialogService = new DialogService();
        SnackbarMessageQueue messageQueue = new SnackbarMessageQueue(TimeSpan.FromSeconds(2));
        INotificationService notificationService = new NotificationService(messageQueue);
        IMessenger messenger = WeakReferenceMessenger.Default;
        MainViewModel mainViewModel = new MainViewModel(fileService, dialogService, notificationService, messenger);

        MainWindow mainWindow = new MainWindow(mainViewModel, messageQueue);
        mainWindow.Show();
    }
}

Chaque objet a besoin d'autres objets, qui doivent exister avant lui. Mis bout à bout, ces besoins forment un graphe de dépendances :

Cet assemblage fonctionne, mais il a trois défauts qui grandissent avec l'application :

  • l'ordre compte : un objet ne peut être créé qu'après ceux dont il dépend ;
  • ajouter un paramètre à un constructeur oblige à modifier l'assemblage ;
  • chaque objet partagé (la file du Snackbar, le Messenger) doit être passé à la main à tous ceux qui en ont besoin.
Depuis PHP — le conteneur de services de Laravel
Dans Laravel, tu n'écris jamais new NoteController(new NoteRepository(…)) : le conteneur de services lit le constructeur du contrôleur, voit qu'il attend une NoteRepositoryInterface, et fournit l'objet enregistré pour ce contrat dans un service provider ($this->app->singleton(NoteRepositoryInterface::class, NoteRepository::class);). C'est exactement ce que fait ServiceCollection en .NET.

Étape 2 — Le conteneur

ServiceCollection, AddSingleton, méthode générique, résolution par le constructeur.

2.1 — Installer le package

Installe le package NuGet Microsoft.Extensions.DependencyInjection, version 10.0.0, dans le projet WpfNotes (et non dans WpfNotes.Core) :

WpfNotes/WpfNotes.csproj
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <UseWPF>true</UseWPF>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="MaterialDesignThemes" Version="5.3.2" />
    <PackageReference Include="Microsoft.Extensions.DependencyInjection" Version="10.0.0" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\WpfNotes.Core\WpfNotes.Core.csproj" />
  </ItemGroup>

</Project>
Point de vigilance — la bibliothèque ignore le conteneur
Seul l'assemblage, dans App, connaît le conteneur. Les ViewModels et les services de WpfNotes.Core continuent de recevoir leurs dépendances par leur constructeur, sans savoir qui les leur fournit : à la main, par un conteneur, ou par un test.

2.2 — Enregistrer, construire, demander

Remplace le contenu de App.xaml.cs :

WpfNotes/App.xaml.cs
using System.Windows;
using CommunityToolkit.Mvvm.Messaging;
using MaterialDesignThemes.Wpf;
using Microsoft.Extensions.DependencyInjection;
using WpfNotes.Core.Services;
using WpfNotes.Core.ViewModels;
using WpfNotes.Services;

namespace WpfNotes;

public partial class App : Application
{
    // Le conteneur d'injection de dépendances, gardé pour être libéré à la fermeture
    private ServiceProvider? _serviceProvider;

    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);

        // 1. Déclarer, pour chaque type demandé, ce que le conteneur doit fournir
        ServiceCollection services = new ServiceCollection();
        services.AddSingleton<IFileService, FileService>();
        services.AddSingleton<IDialogService, DialogService>();
        services.AddSingleton<SnackbarMessageQueue>(new SnackbarMessageQueue(TimeSpan.FromSeconds(2)));
        services.AddSingleton<INotificationService, NotificationService>();
        services.AddSingleton<IMessenger>(WeakReferenceMessenger.Default);
        services.AddSingleton<MainViewModel>();
        services.AddSingleton<MainWindow>();

        // 2. Construire le conteneur
        _serviceProvider = services.BuildServiceProvider();

        // 3. Lui demander la fenêtre : il crée tout ce dont elle a besoin, dans le bon ordre
        MainWindow mainWindow = _serviceProvider.GetRequiredService<MainWindow>();
        mainWindow.Show();
    }

    protected override void OnExit(ExitEventArgs e)
    {
        if (_serviceProvider != null)
        {
            _serviceProvider.Dispose();
        }
        base.OnExit(e);
    }
}
Depuis PHP — une méthode générique
AddSingleton<IFileService, FileService>() est une méthode générique : entre les chevrons, on ne lui passe pas des valeurs mais des types. PHP n'a pas d'équivalent direct ; le plus proche est de passer des noms de classe, comme singleton(FileServiceInterface::class, FileService::class). Tu as déjà utilisé des types génériques sans le dire : List<Note>, IRecipient<NoteSavedMessage>.
Ce que fait ce code
  • 1. ServiceCollection — la liste des enregistrements :
    • AddSingleton<IFileService, FileService>() — « quand on demande un IFileService, fournis un FileService ». Le conteneur le créera lui-même.
    • AddSingleton<SnackbarMessageQueue>(new SnackbarMessageQueue(…)) — ici, on fournit l'objet déjà créé : le conteneur ne saurait pas quelle durée passer au constructeur.
    • AddSingleton<IMessenger>(WeakReferenceMessenger.Default) — de même, l'instance partagée du Toolkit.
    • AddSingleton<MainViewModel>() et AddSingleton<MainWindow>() — des classes concrètes, demandées telles quelles.
  • 2. BuildServiceProvider() — construit le conteneur à partir de la liste.
  • 3. GetRequiredService<MainWindow>() — demande la fenêtre. Le conteneur lit son constructeur, voit qu'il attend un MainViewModel et une SnackbarMessageQueue, crée d'abord le MainViewModel (qui attend lui-même quatre services, créés avant lui), et ainsi de suite. C'est le graphe de l'étape 1, parcouru automatiquement.
  • OnExit — à la fermeture, Dispose() libère le conteneur et les objets qu'il a créés. _serviceProvider est déclaré ServiceProvider? : il vaut null jusqu'au démarrage, d'où le test avant de l'utiliser.
Notion — singleton ou transient ?
AddSingleton signifie : un seul objet pour toute l'application, créé à la première demande puis toujours le même. L'autre durée de vie courante est AddTransient : un objet neuf à chaque demande (le bind de Laravel, quand singleton est l'équivalent de AddSingleton). Ici, tout est singleton : les services sont partagés, et les NoteViewModel, qui doivent être neufs pour chaque note, ne passent pas par le conteneur : MainViewModel les crée lui-même.

Étape 3 — Rien d'autre n'a changé

La preuve par Git, et une erreur à savoir lire.

Avant de commiter, regarde la liste des fichiers modifiés depuis le sprint 6 :

Terminal — à la racine de la solution
git status

Seuls App.xaml.cs et WpfNotes.csproj ont changé. Aucun ViewModel, aucun service, aucune vue : c'est le bénéfice d'avoir fait recevoir ses dépendances à chaque classe. On a changé qui fournit les objets, sans toucher à ceux qui les utilisent.

À tester (F5)
L'application se comporte exactement comme au sprint 6 : liste, création, enregistrement, suppression avec confirmation.
Point de vigilance — un service oublié

Mets en commentaire la ligne services.AddSingleton<INotificationService, NotificationService>();, puis lance avec F5. L'application s'arrête au démarrage sur une exception :

Message d'erreur (extrait)
Unable to resolve service for type 'WpfNotes.Core.Services.INotificationService'
while attempting to activate 'WpfNotes.Core.ViewModels.MainViewModel'.

Il se lit ainsi : « en créant MainViewModel, je n'ai trouvé aucun enregistrement pour INotificationService ». Le second nom dit qui le demande, le premier ce qui manque. Remets la ligne avant de continuer.

Bilan des notions vues

NotionÉtapeRôle dans le TP
Graphe de dépendances1Qui a besoin de qui, et dans quel ordre créer les objets.
Conteneur d'injection2Crée et assemble les objets à partir des enregistrements.
ServiceCollection2La liste des enregistrements.
Méthode générique2AddSingleton<IFileService, FileService>() : des types en paramètres.
GetRequiredService2Demander un objet ; le conteneur résout tout le graphe.
Singleton / transient2Un objet partagé, ou un objet neuf à chaque demande.
Dispose2Libérer le conteneur à la fermeture.
